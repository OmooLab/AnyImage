## Context

后端 Server 和控制进程已有顺序执行队列。Blender 侧使用唯一 `active_job`，Operator modal 读取该全局引用，Runtime 的进度与取消也只覆盖一个任务。当前 AnyImage 的 AI 入口用 `not is_busy()` 禁止连续提交。

本改动跨 BlendJob 和 AnyImage，复用既有队列、状态消息和 Blender 翻译机制。

## Goals

- 用户连续点击多个图像操作即可排队，每个任务独立应用结果与释放输入。
- 开发者继承 `JobOperator`，继续实现 `request()`、`response()`、`cleanup()`。
- 侧边栏仅需 `runtime.draw_jobs(layout)`；执行资格只需 `runtime.can_submit()`。
- 以 FIFO 串行执行控制显存、内存和结果顺序。

## Decisions

### 1. 单一任务集合与单次任务绑定

Runtime 使用按提交顺序保存的 Job 集合替代 `active_job`；Job 保存 ID、所属 Operator、controller、目录、状态和进度。Operator modal 绑定自己的 Job，不读取“当前全局任务”。公共 API 不暴露第二套队列管理抽象。

控制进程继续顺序执行提交，Blender 仅跟踪任务和消费结果。控制进程必须在接收命令时立即发布 queued 状态，使等待任务不会误显示为执行中。各任务主线程结果按提交顺序应用，避免不同 modal 轮询顺序造成后提交结果先写回。

Job 达到终态后释放执行资格；response/cleanup 使用该任务的局部引用。每个任务的结果处理至多一次，cleanup 恰好一次。失败报告通过原 Operator；后续任务继续执行。

### 2. 三个明确的调用入口

```python
class RemoveBackground(runtime.JobOperator, bpy.types.Operator):
    job_type = "remove-background"
    # request / response / cleanup 保持原来的职责

row.enabled = runtime.can_submit()
runtime.draw_jobs(layout)
```

`JobOperatorBase` 的类、导出、属性、文档和测试统一改为 `JobOperator`。删除 `is_busy()` 及单任务进度、取消入口的旧实现，不提供旧名称别名。

`can_submit()` 在 `OFFLINE`、`STARTING`、`IDLE`、`PROCESSING` 为真。首次提交自动启动，启动期间后续提交加入队列；在未安装、安装、迁移、停止和错误状态为假。只有后端终态才能释放任务的执行占用，不能在发送取消请求时提前允许资源卸载。

`state()` 保持现有状态集合：存在排队或执行任务时为 `PROCESSING`，启动、停止和维护状态按现有优先级展示；任务全部结束后依据服务器快照恢复 `IDLE`、`OFFLINE` 或 `ERROR`。

### 3. 状态栏与任务列表

开发者可在任意布局调用 `runtime.draw_jobs(layout)`；AnyImage 选择服务器侧边栏。按提交顺序绘制未结束任务，每行只含 `layout.progress(type="BAR", text=...)` 和一个取消按钮。

等待任务显示零进度及“等待中”；执行任务使用已翻译的进度消息；取消请求等待确认期间显示“取消中”。按钮带目标 Job ID，不依赖选中对象。完成、失败、取消后移除行，空列表不占空间。安装、迁移等现有长操作也使用同一绘制入口。

Runtime 注册状态栏 draw callback，自动显示按提交顺序找到的第一个运行任务，复用任务行的进度、翻译和取消按钮。结束后切换到下一个运行任务，没有运行任务时隐藏。状态栏与任意布局中的列表都会刷新，列表关闭不影响状态栏和任务执行。

### 4. 取消与维护围绕任务身份执行

点击某行取消只取消该 Job，排队任务不会运行；运行任务等后端确认取消后释放临时文件。ESC 只作用于收到事件的任务 Operator，处理后消费事件，防止一次按键连带取消整个列表。

停止、重启和迁移先进入禁止提交的过渡状态，取消所有未结束任务，再等待后端结束及主线程清理。迁移随后停止服务、搬移和保存配置；重启在停止后重新启动。维护进行中阻止重复维护，成功结果与取消竞争时取消优先，避免维护过程中写回图像。

单个任务超时取消需要强制停止服务时，明确终结受影响的执行任务；尚未开始的任务保留并按顺序重启服务执行。用户主动停止或维护则终结整批队列。控制进程退出时，所有受影响 Job 均终结并清理，不能留下永久等待的行。

### 5. AnyImage 保存提交时的输入与目标

每次操作在主线程捕获目标、模型参数及输入文件，使用独立临时路径；不以全局当前对象作为异步结果目标。同一图像重复提交各自使用提交时输入，成功结果按提交顺序写回。

目标被删除或绑定发生变化时，验证已捕获目标是否仍可应用；无法安全应用则报告该任务失败并清理，不修改当前选中的其他对象。审查去背景、高清、平面、全景、选区相关任务与共享输入辅助函数。

生成入口用 `can_submit()`，安装入口独立判断 `UNAVAILABLE`。缺少模型时保留已有模型准备提示；运行中本身不再阻止点击。

## Risks / Trade-offs

- 大量排队输入占用磁盘 → 每 Job 独立目录，取消确认及终态后及时清理临时输入，保留既有输出文件策略。
- modal 交错导致重复清理或乱序结果 → Job 身份和终态收敛统一处理，测试乱序轮询、response 抛错及取消竞争。
- 停止进程影响多个任务 → 区分单行取消与整队停止，测试强制停止后的任务收敛和后续队列恢复。
- 两仓库依赖需同步 → 同批更新 API、所有调用和本地 wheel，检查锁文件及 Manifest。

## Migration Plan

先修改 BlendJob 的任务集合、Operator 绑定和队列终态，再接入列表 UI、取消与维护；随后更新 AnyImage 调用、输入隔离和文档。移除旧符号并运行相关测试，最后同步本地 wheel 与依赖锁。交付为一个完整 API 迁移，回退时两个仓库与依赖一起回退。
